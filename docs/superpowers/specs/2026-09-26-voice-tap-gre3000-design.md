# 声控手机助手（voice_tap）设计文档

- 日期：2026-09-26
- 状态：已与用户确认，待写实施计划
- 目标场景：Windows 上用 scrcpy 看安卓手机，玩 GRE3000 背单词时用语音代替鼠标点击

---

## 1. 问题与目标

### 1.1 现状

用户在 Windows 上通过 `H:\scrcpy-win64-v4.1\scrcpy.exe` 投屏并控制安卓手机。使用 GRE3000 背单词 App 时，界面为选择题：上方显示中文或英文题干，下方提供若干单词选项，用户需要点选正确答案。长时间用鼠标点击导致手部疲劳。

### 1.2 目标

用户开口说出答案单词，工具自动在当前手机屏幕上定位该单词对应的可点击区域并点击，全程不需要鼠标或键盘参与。

### 1.3 非目标（本期明确不做）

- 语音纠正指令（如"不对，是 apple"）
- TTS 语音播报反馈
- 自动连续答题 / 自动判断答案
- 图形界面（GUI）
- 多邻国（Duolingo）等自绘界面 App 的支持 —— 留待第二期
- 题目理解、语义推理 —— 本工具只做"文字定位与点击"，不理解词义

### 1.4 成功标准

在安静环境下，用户说出屏幕上存在的选项单词，工具能在 3 秒内完成识别、定位、点击，且点击位置准确落在该选项的可点击区域内。对屏幕上不存在的词，工具绝不产生误点击。

## 2. 环境约束与关键前提

| 项目 | 情况 |
|---|---|
| 手机连接方式 | adb（scrcpy 自带的 adb server） |
| adb 可执行文件 | 优先 `H:\scrcpy-win64-v4.1\adb.exe`，其次系统 PATH |
| 运行平台 | Windows（用户本机），Python 已安装（要求 3.9+，具体版本由 `probe.py` 阶段确认） |
| 开发环境 | 开发者侧为 Linux 沙箱，**无法连接真机、无法访问 scrcpy 目录** |
| 麦克风 | 用户本机默认输入设备 |

### 2.1 由此产生的开发方式

开发者无法真机验证，因此采用"用户执行 + 反馈"的协作闭环：

1. 第一个交付物是**探测脚本 `probe.py`**，用于实证 GRE3000 是否支持无障碍树读取。
2. 主工具内置 **`--preview` 模式**，将匹配与点击决策可视化到截图上，用户截图反馈。
3. 纯逻辑部分（匹配引擎、XML 解析）由开发者用单元测试在本地保证正确性。

这是本项目的核心风险缓解手段，不是可选项。

## 3. 总体架构

### 3.1 核心链路

```
麦克风 ─▶ 静音检测切句 ─▶ Whisper 转文字 ─┐
                                          ├─▶ 匹配引擎 ─▶ 点击
              ┌───────────────────────────┘
        （检测到开口瞬间并发触发界面抓取）
         adb 抓界面 ─▶ 无障碍树解析 ─▶ 节点列表
                          │ 可点击文字节点 < 3
                          ▼
                    截图 + OCR（第二期）
```

### 3.2 解耦设计

所有模块通过统一数据结构耦合：

```python
Node = (text: str, x: int, y: int, clickable: bool, source: str)
# source ∈ {"uiautomator", "ocr"}
```

匹配引擎完全不知道文字来源，因此第二期接入 OCR 时无需改动上层逻辑。

## 4. 模块设计

### 4.1 `adb.py`

**职责**：封装所有对 adb 的调用，向上层提供干净的函数接口。

**接口**

```python
def find_adb() -> str
def devices() -> list[str]
def dump_ui(timeout: float = 10.0) -> str          # 返回 XML 字符串
def screencap(timeout: float = 10.0) -> bytes
def tap(x: int, y: int) -> None
```

**关键实现要点**

- `dump_ui` 使用两步式：`adb shell uiautomator dump /sdcard/voice_tap.xml`，随后 `adb exec-out cat /sdcard/voice_tap.xml`。不采用 `dump /dev/tty`，因为该方式在多版本 Android 上行为不一致。
- **必须处理 "could not get idle state" 错误**：界面动画期间 dump 会失败，需自动重试最多 2 次，每次间隔 300ms。这是该方案最常见的失败模式。
- 所有 subprocess 调用设置 `timeout`，避免 adb 无响应时进程挂死。
- `tap` 使用 `adb shell input tap X Y`。
- 若 adb 未找到设备，抛出带明确中文提示的异常，由上层捕获并打印。

### 4.2 `screen.py`

**职责**：把"当前屏幕上有哪些文字、各在哪里、能不能点"这件事抽象出来。

**接口**

```python
class ScreenReader:
    def capture(self, force: bool = False) -> list[Node]
    def get_options(self) -> list[Node]      # 仅返回可点击节点
```

**UIAutomator 路径**

解析 XML，对每个含 `text` 属性的节点：

1. 记录 `text` 与 `bounds` 中心。
2. 若该节点 `clickable="false"`，**向上回溯到最近的可点击祖先节点**，用于确认"这个文字确实是可点的"。
3. 计算实际点击坐标时，**优先取文字节点自己的中心**，前提是该中心落在可点击祖先的 bounds 范围内；只有中心不在可点范围内时才退而使用祖先中心。

第 3 条的取舍经过实测验证：初版设计是直接点祖先中心，但遇到"大容器套小图标"的布局（例如容器 bounds 覆盖整条底部栏、图标只占右下一角）时，祖先中心会离目标图标很远，点击偏移可达数百像素。改用"文字中心优先、祖先中心兜底"后，选项整行可点的情况仍落在选项正中，图标情况也能精确命中。该逻辑已在沙箱中以合成 XML 覆盖四种场景验证（选项整行可点 / 大容器套小图标 / 文字中心跑出可点范围 / 空树）。

4. 若向上回溯不到任何可点击祖先，则保留文字自身坐标，并标记 `clickable=False`。这类节点在匹配时优先级最低。

**降级判定**

若解析结果中 `clickable=True` 的文本节点少于 3 个，判定为自绘界面（Flutter / 游戏引擎 / Canvas），标记需要走 OCR 路径。第一期在此时打印明确提示并中止本次操作；第二期接入 OCR。

**帧缓存**

`capture()` 结果按时间戳缓存。同一帧内重复调用（例如并发触发的预抓取与正式匹配）不重复 dump。

**并发预抓取**

提供 `prefetch_async()`，在 VAD 检测到用户开口的瞬间启动后台 dump。用户说完时界面数据通常已就绪，可省下约 1 秒延迟。

### 4.3 `asr.py`

**职责**：把麦克风里的声音变成文字，并给出置信度。

**采集参数**：16kHz 采样率、单声道、16-bit PCM。使用 `sounddevice`（Windows 上 wheel 自带 PortAudio，无需额外安装）。

**VAD 策略（能量阈值法）**

- 起始判定：连续 3 帧 RMS 超过阈值视为开口。该事件立即触发 `screen.prefetch_async()`。
- 结束判定：尾部静音持续超过 0.4 秒视为说完。
- 硬上限：单句最长 6 秒，超时强制截断送识别。
- 阈值、静音时长、最长句长均可在 `config.yaml` 调整。

选择能量 VAD 而非 `webrtcvad`/`silero-vad` 的理由：零额外依赖、在安静室内环境足够可靠、调试直观（用户可以看着音量条理解为什么没触发）。若实际使用中噪声误触发严重，再考虑替换。

**识别**

- 引擎：`faster-whisper`，CPU 推理，`compute_type="int8"`。
- 模型：默认 `small`（多语言，中英文都能识别）。体积约 480MB。若准确率不足可上调至 `medium`，追求速度可下调至 `base`。
- **模型下载走国内镜像**：设置环境变量 `HF_ENDPOINT=https://hf-mirror.com`。不设置则 HuggingFace 直连在国内会长时间卡住。
- 输出 `(text: str, avg_logprob: float)`，`avg_logprob` 用于置信度判断。

**接口**

```python
class Recognizer:
    def listen_once(self, timeout: float | None = None) -> tuple[str, float] | None
    def start_continuous(self, on_utterance: Callable) -> None
    def stop(self) -> None
```

### 4.4 `matcher.py`

**职责**：把识别出的文字匹配到屏幕节点上，输出点击坐标。这是本项目最需要打磨的模块。

**归一化**

统一处理：转小写 → 去首尾空白 → 去除首尾标点与句号 → 全角转半角 → 折叠连续空格。

**匹配策略（逐级降级）**

| 级别 | 规则 | 说明 |
|---|---|---|
| 1 | 归一化后完全相等 | 最可信 |
| 2 | 一方包含另一方，且较短方长度 > 2 | 容忍 "apple" 匹配到 "apple n.苹果" |
| 3 | 编辑距离 ≤ 1，且双方长度 ≥ 4 | 容忍 ASR 听错一个字母，如 apple → aple |
| 4 | 无匹配 | **放弃，不点击** |

长度门槛（>2、≥4）用于避免 "a"、"an" 这类短词匹配到一大片。

**候选范围**

优先只在 `clickable=True` 的节点中匹配。若该范围内无结果，再扩大到全部节点。

这一策略天然解决了"题干文字与选项文字撞车"的问题：题干通常不可点击，会被自动排除。

**多匹配处理**

在候选范围内按"从上到下、从左到右"排序，取第一个，同时打印告警列出所有匹配项，便于用户发现异常。

**接口**

```python
@dataclass
class MatchResult:
    node: Node | None
    level: int          # 1/2/3，0 表示未匹配
    candidates: list[Node]

def match(text: str, nodes: list[Node]) -> MatchResult
```

`match` 为纯函数，无副作用，可用单元测试完整覆盖。

### 4.5 `clicker.py`

**职责**：执行点击，并防止连点。

- 调用 `adb.tap(x, y)`。
- 防连点：距上次点击 800ms 内的新指令直接丢弃并打印提示。
- 点击成功后再等待 300ms 才接受下一次，避免界面切换瞬间的重复触发。
- **`preview` 模式**：不实际点击，改为在截图上以红圈标出目标位置，连同识别文字、匹配级别一并存到 `debug/` 目录。

### 4.6 `hotkey.py`

**职责**：全局热键监听与模式切换。

- 使用 `keyboard` 库注册全局热键，不依赖窗口焦点（scrcpy 窗口保持焦点时同样生效）。
- `F8`：`hotkey` 模式下按住说话、松开触发识别与点击。
- `F9`：在 `listen` 与 `hotkey` 两种模式间热切换，运行时生效，无需重启。
- `Esc` 或 `Ctrl+C`：退出。

热键可在 `config.yaml` 中修改。

### 4.7 `feedback.py`

**职责**：统一的日志输出与可选提示音。

日志分步打印，每步都带足够信息，使失败原因一眼可辨：

```
[听到] apple  (置信度 0.82)
[屏幕] 无障碍树读取成功，可点击文字节点 4 个
[匹配] 精确命中 "apple"  →  (540, 1420)
[点击] 完成
```

失败时打印屏幕上实际存在的可点击文字：

```
[匹配] 未找到 "aple"
[屏幕] 当前可点击选项：apple / banana / orange / grape
```

这一条是排查体验的关键：用户可据此立刻区分"发音被听错了"还是"屏幕上根本没有这个词"。

提示音默认关闭（避免打扰），可在配置中开启。

### 4.8 序号匹配（2026-09-26 追加）

**动机**：用户反馈「生僻词匹配不上」。GRE3000 的选项里有「骄奢淫逸的，耽于感官享受的」
这种长词，ASR 听错的概率不低。而「1、2、3」几乎不可能听错 —— 直接说序号是最稳的退路。

**支持的表达**：`1` `一` `第一个` `第1个` `选三` `我选2` `第五个` `选项2` `最后一个`

**优先级的取舍**：序号检查排在所有文字匹配之前。理由是说序号是最明确的意图，
不该被文字匹配抢走。但**序号超出选项数量时不直接放弃**，而是落回文字匹配 ——
万一选项文字里真有个数字呢。两层都不中，才报「你说了第 N 个，但屏幕上只有 M 个选项」。

有个边界要留意：最小长度门槛（防止「的」命中一大片）会让单字符无法参与子串匹配，
而 `"9"` 正是单字符。所以规则调整为**纯数字不受该门槛限制** —— 数字是具体记号不是常见字，
且选项里出现数字往往就是它的本意。

### 4.9 小键盘快捷点击（2026-09-26 追加）

按小键盘 1~9 直接点对应选项，不用说话。为空口环境（开会、家里有人睡觉）准备的。

**关键实现细节**：不能简单地监听 `'1'`..`'9'`。

`keyboard` 库把**小键盘数字和主键盘数字映射成了同一个键名**（都是 `'1'`..`'9'`），
按名字监听会把用户在任何程序里打的数字都抢走。查过库源码后确认：
小键盘的扫描码 `0x60`–`0x69` 会展成 `("0","1",...,"9")`，而主键盘的 `0x30`–`0x39`
也展成同样的名字，**光看名字区分不了**。

真正的区分依据是事件对象上的 `is_keypad` 字段 —— 那是库拿扫描码、虚拟键码和扩展位
跟内置的 `keypad_keys` 表比对算出来的。所以实现改用 `keyboard.hook()` 拿底层事件，
只在 `is_keypad` 为真时理会。**主键盘的数字键完全不受影响。**

**NumLock 的影响**：NumLock 关着时，小键盘产生的是方向键事件（`is_keypad` 仍为真，
但键名是 `down`/`end` 之类）。这时会给出一次性提示让用户去开 NumLock，
不做静默失败 —— 否则用户会以为程序坏了。

**线程模型**：小键盘由**独立工作线程**处理，不放在主循环里。
因为常驻监听模式下主循环会一直阻塞在「等你说话」上，那时按小键盘就没有任何反应。
代价是两条路径可能并发点击，所以 `Clicker` 的防连点判断必须加锁
（原来是「先检查再赋值」，两个线程会同过）。

**默认关闭**。虽然只截小键盘、风险很低，但「按个数字就点一下」这种事还是让用户
自己决定什么时候开。`F10` 运行时切换。

### 4.10 点击出口统一

语音路径（`handle_speech`）和小键盘路径（`handle_numpad`）共用同一个
`do_click()` 出口，因此防连点、preview 画圈、预抓取作废这三件事的行为完全一致，
不会出现「语音点得对、小键盘点得歪」这种分裂。

两条路径在取屏幕上**有意不同**：语音路径优先用预抓取结果（说话那一两秒正好够抓界面），
小键盘路径必须现抓 —— 按键是「按下去那一刻才决定」的，用缓存可能拿到上一题的界面。

### 4.11 坐标复用方案的推翻（2026-09-26 追加，重要）

**背景**：用户提出「GRE3000 选项位置固定，小键盘按了直接点对应位置会不会更快」。
为此先后实现了两套「复用坐标」的提速方案：

1. **坐标缓存 + 快速通道**：缓存上次真实读屏的坐标，按键时直接用缓存点，
   点前做一次轻量的前台应用检查，点后后台刷新。
2. **固定坐标模式**：把坐标写进配置，纯算术点击，完全不读屏。

**用户实测后反馈：「固定坐标点选项的还是不好」。两套方案都已移除。**

**为什么错**：两个方案共享同一个错误前提 —— 以为坐标可以复用。实测数据否定了它：

| 选项 | 观测到的 y |
|---|---|
| 1 | 811（三次一致） |
| 2 | 999 |
| 3 | 1187 |
| 4 | **1375、1418** |
| 5 | 1563 |

五行严格等距、公差 188，这一点可靠。但第 4 个选项出现过 1418，差 43 像素，
对应那一题的题干明显更长。选项行高 150，中心到行边界仅 75 像素 ——
43 像素的偏移已吃掉大半余量，题干再长就可能跨到相邻选项。

**关键在于失败的形态**：它会**点了、不报错、只是位置不对**。用户不会察觉，
除非正好注意到答错了。而这道工具的整个设计原则是「宁可漏点，不可错点」——
把「精确」换成「猜」，方向本身就和原则相悖。

**推翻这个前提之后看，整个优化是在解决一个不存在的问题**：
`uiautomator dump` 一次就同时返回**文字和当前坐标**（同一个 XML 节点里的
`bounds="[x1,y1][x2,y2]"`，由系统报出）。既然一次读屏就能拿到这一题的精确坐标，
就没有任何理由去用上一题的坐标。

**因此：选项只有一条路 —— 读屏 → 用系统报的坐标点。**
提速的正确方向是优化读屏本身，而不是绕开它。

**已做的读屏优化**：原来读一次要两次 adb 往返（先 `uiautomator dump` 到文件、
再 `exec-out cat` 取回）。现合并为一条命令
`uiautomator dump <file> >/dev/null; cat <file>`，少一次进程创建
（在 Windows 上每次 adb 调用都是一次进程创建）。保留两步式作为失败回退，
因为两步式能给出更具体的错误信息。

保留的能力：`--calibrate` 标定命令、`fixed_next_position`（见 4.12）。

### 4.12 「下一题」按钮（2026-09-26 追加）

答错或点「不记得了」之后会翻到词汇详情页，需要点「下一题」才能继续。

**页面识别**：详情页没有 `tv_question`，原来会被判成「不在答题页」。
现在 `read_screen` 增加页面类型（`quiz` / `detail` / `other`）：
没有选项但找到「下一题」类按钮时判为详情页，并把按钮一并返回。

**按钮靠文字匹配**（`下一题 / 下一词 / 继续 …`）。2026-09-26 实测确认文字**就是「下一题」**，
坐标 **(909, 2476)** —— 在页面底部。

**小键盘 `0` 绑定它** —— 没有「第 0 个选项」，而 0 是最好按的键，正好给它。

**这是唯一保留固定坐标的地方**，理由和选项相反：它是页面底部的固定控件，
**不随题干长短漂移**。已写进 `config.yaml` 的 `hotkey.fixed_next_position`。
留空则每次读屏去找按钮。

**遗留问题**：标定是在「有 5 个选项 + 底部有下一题按钮」的状态下做的。
如果真正的详情页上按钮在别的位置，固定坐标会点空 —— 用户下次使用时留意，
点不到就把配置改回 `null` 走读屏。

### 4.13 题干长度与选项位置的关系（2026-09-26 实测补全）

三次标定给出了清晰的分界：

| 题干 | 字符数 | 第 4 个选项的 y |
|---|---|---|
| `degrade` | 7 | 1375 |
| `to feel or express annoyance or ill will at` | 43 | 1375 |
| `standing out conspicuously : prominent; especially : of notable significance` | ~70 | **1418** |

43 字符及以下位置完全不变（五行仍是 `811 / 999 / 1187 / 1375 / 1563`），
70 字符时整体下移 43 像素。**分界点在 43 与 70 之间，大概率是题干折成两行的那个点。**

这条数据同时说明两件事：

1. 它印证了「选项不能固定坐标」的判断 —— 而且给出了边界在哪。
2. 短题干（≤43 字符）下位置是稳的，所以如果将来要重新评估，边界是已知的。

但结论不变：**既然读屏一次就同时拿到文字和当前坐标，就没有理由去赌题干长度。**

## 6. 容错行为汇总

| 情况 | 行为 |
|---|---|
| 未识别到语音 / 识别结果为空 | 不点击，打印提示，等待下一句 |
| 屏幕上无匹配词 | 不点击，列出屏幕实际可点击文字 |
| 匹配到多个候选 | 按屏幕顺序取第一个 + 打印告警 |
| 无障碍树读取失败 | 自动重试 2 次；仍失败则本次放弃并打印原因 |
| 可点击文字节点 < 3（自绘界面） | 第一期：打印"该界面不支持无障碍读取"并放弃；第二期：转 OCR |
| adb 设备掉线 | 打印明确错误并尝试重连一次 |
| 识别置信度低于阈值 | 打印告警，仍执行点击（可通过配置改为不点） |

设计原则：**宁可漏点，不可错点。** 背单词场景下点错会被判错，而漏点只需重说一遍，代价不对称。

### 6.1 前台应用护栏（必须实现）

**来源**：2026-09-26 的一次探测中，手机前台停在 QQ 上而不是 GRE3000。探测脚本照常读出了 286 个节点、
43 个可点击文字，并给出「无障碍树可用」的结论 —— 它忠实地完成了工作，但这份数据毫无意义，
而且如果主程序在这种状态下直接执行点击，就会去点 QQ 里的东西。

**规则**：每次点击前必须校验当前前台应用，两个条件同时满足才允许点击：

1. 前台包名等于 `com.enhance.greapp`
2. 无障碍树里能找到至少 2 个 `com.enhance.greapp:id/tv_question` 节点

任一条件不满足就**拒绝点击**，并明确提示用户「当前不在 GRE3000 答题界面（检测到：<包名>），请切回去」。

**理由**：声控工具是"盲点"的 —— 用户看不见程序看到了什么。如果它把 QQ 的会话列表当成选项去点，
后果不可预期（可能点进某个群、可能发出消息）。加一道校验的成本极低，但能杜绝一整类事故。

**顺带的好处**：这条校验也让程序能明确区分「GRE3000 没打开」和「GRE3000 打开着但不在答题页」，
用户看到提示就知道该做什么。

## 7. 测试与验证策略

因开发者无法连接真机，验证分两层。

### 7.1 开发者侧（可完全自主完成）

- `matcher.py` 的 `match()` 是纯函数，用单元测试覆盖：精确匹配、包含匹配、编辑距离匹配、多候选消歧、无匹配、全角半角混排、大小写混排、标点干扰、短词长度门槛。
- `screen.py` 的 XML 解析使用 `tests/fixtures/` 中的假 XML 覆盖：普通原生界面、文字节点不可点击需回溯祖先、自绘界面（节点稀少）、bounds 缺失等边界情况。
- 目标：这两个模块的逻辑正确性由测试而非真机验证保证。

### 7.2 用户侧（实证验证）

- `probe.py`：自动定位 adb、连接设备、抓取当前界面，输出并保存三样东西到 `debug/`：
  1. uiautomator 原始 XML
  2. 当前屏幕截图 PNG
  3. 统计摘要（例如"屏幕下半部分找到 4 个可点击文字节点：apple / banana / orange / grape"）

  用户把摘要与 XML 反馈给开发者，即可确证 GRE3000 的实际界面结构，避免在错误假设上开发。

- `--preview` 模式：主程序在每次决策后不实际点击，而是把目标位置以红圈标注在截图上存入 `debug/`。用户截图反馈，开发者可远程定位问题出在哪一环。

### 7.3 探测脚本作为第一交付物的理由

GRE3000 是否使用原生安卓控件（而非 Flutter / Canvas / WebView）直接决定本条技术路线是否成立。这是一切的前提假设，必须在写主程序之前用真实数据证实。因此 `probe.py` 排在实施计划的第一步，其产出是后续所有工作的输入。

若探测结果表明 GRE3000 为自绘界面，则需重新评估方案（大概率改为 OCR 优先），此时设计文档需相应修订。

## 9. 已确认的设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 屏幕文字获取 | 无障碍树优先，预留 OCR 降级 | GRE3000 走快通道，多邻国走通用通道，一套代码 |
| 语音识别 | 本地 Whisper，完全离线 | 用户选择；隐私好、无需联网、无 API 成本 |
| 触发方式 | 常驻监听 + 热键，F9 热切换 | 用户要求灵活；两种模式并存成本很低 |
| 程序形态 | 命令行窗口 + 分步日志 | 调试期价值最高，出错可一眼定位 |
| 匹配失败 | 不点击 | 错点会被判错，漏点只需重说，代价不对称 |
| 交付方式 | 标准 Python 项目 | 用户已有 Python；开发者无法跨平台打包 exe |
| 识别置信度低 | 打印告警但仍点击 | 可配置为不点；默认倾向于减少操作摩擦 |
