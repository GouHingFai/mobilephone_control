# 声控手机助手 —— 可视化界面与语音「下一题」设计文档

- 日期：2026-09-27
- 状态：已与用户确认，待写实施计划
- 关联文档：`2026-09-26-voice-tap-gre3000-design.md`（主程序设计）
- 本期的三件事：加一个**置顶浮窗**、补上**语音说「下一题」**、修**连按两下同一个键会点到新题上**的 bug

---

## 1. 背景与目标

### 1.1 现状

主程序已经能用（命令行窗口 + 分步日志），语音和小键盘两条路都在真机上跑通。
但用户是通过 scrcpy 看着手机操作的，而程序的内部状态（它读到哪一屏、识别成了什么、
按下的键有没有生效）全都在**命令行窗口里刷屏**，用户看不过来，也不好核对。

### 1.2 三个诉求

1. **可视化界面**，放在 scrcpy 上面，随时能看到三件事：
   - 各项功能的开关状态，并能直接点它开/关；
   - 程序**手里那一屏**（也就是会拿去做预读点击的那一屏）的选项，用来核对「读屏读对了没有」；
   - 最近一次识别出的语音内容、以及按下的小键盘键，用来核对「我的选择/输入有没有被正确收到」。
2. **语音说「下一题」**：答错后进详情页，现在只能按小键盘 `0` 或用鼠标点。
   希望直接说一句「下一题」就能继续。
3. **修 bug**：连按两下同一个数字键（如 `1`、`1`），第二下被推到翻页**之后**才执行，
   于是照着**新题目**点了第 1 个选项。

### 1.3 非目标（本期明确不做）

- **界面显示坐标** —— 用户明确不要，说「没有意义」。坐标仍然打进日志，供排查用。
- 自动吸附到 scrcpy 窗口旁边（要靠 Windows 接口查别人的窗口位置，复杂且易失效）。
- 界面与主程序分成两个进程（多进程隔离）—— 对这个工具是杀鸡用牛刀。
- 历史记录持久化、题目统计等 —— 没有需求。
- 界面里做 OCR / 多邻国支持 —— 属于第二期。

### 1.4 成功标准

- 浮窗**始终浮在最上层**，可以拖到 scrcpy 旁边；位置和大小记住，下次启动照旧。
- 三块信息在程序运行时**持续刷新**，一眼能看出「它现在读到什么、听到什么、按了什么」。
- 界面上的开关点一下**立刻生效**（≤ 0.3 秒），且与热键（F7/F9/F10）状态**始终一致**。
- 答错进详情页后，说一句「下一题」能点下去。
- 连按两下同一个数字键：**只发生一次点击**，且**绝不会**点到翻页后的新题目上。
- 关窗口能立刻退出（不再出现「按了 ESC 还要等你说完这句才退」）。

## 2. 需求细节

### 2.1 界面三块的内容

**① 控制区**（点了立刻生效，状态与热键同步）

| 控件 | 作用 | 等价热键 |
|---|---|---|
| 语音开关 | 开/关语音识别 | `F7` |
| 模式 | 「常驻监听 ⇄ 按住说话」 | `F9` |
| 小键盘 | 开/关小键盘快捷点击 | `F10` |
| 点击后预读 | 开/关 `prefetch.after_click` | 无 |
| 语音说「下一题」 | 开/关本期新增的这条语音控制 | 无 |
| 强制重新读屏 | 同小键盘 `.` | 无 |
| 退出 | 关程序 | `ESC` |

**② 读屏区**：题干 + 各选项的**文字**（带序号）+ 来源（预读 / 当场读屏）+ 多久前读的。
**不显示坐标。** 若当前没有可用的界面数据，明确显示「尚未读到」。

**③ 我的输入区**：最近一次识别出的文字（含置信度）、最近按下的小键盘键、
最近一次点击的**结果**——成功点的第几个 / 被忽略（及原因）/ 没匹配上。

### 2.2 语音「下一题」

识别出的文字里包含控制语（`下一题 / 下一词 / 下一个 / 继续 / next`）时，
**直接复用 `handle_next()` 点下去**，不另外读屏校验（**直给版**）。

用户明确选择了直给版，理由是：「如果是答题页，点了就点了」。
即：在答题页上误说「下一题」，程序照着固定坐标点下去，这是用户接受的代价。

控制语**优先于**选项文字匹配 —— 否则「下一题」会被拿去和选项比对，永远匹配不上。

### 2.3 动作时戳（修 bug）

**规则一句话：一个按键动作，只有当「它准备点击的那一屏」和「按键那一刻用户面前的屏」
是同一屏时，才允许执行。**

**为什么需要它**（bug 的成因）：小键盘按键先入队列，由工作线程逐个处理。
在第一题上连按两下 `1` 时：

1. 第一下出队 → 用预读好的坐标点中第 1 个 → `invalidate()` 作废缓存 + 启动后台预读去读**下一题**；
2. 第二下还在队列里排队；
3. 工作线程回头处理它 → 要「拿当前界面」→ 缓存刚作废、后台预读**正读着** →
   `take_or_wait()` **等它读完**（最坏 8 秒）；
4. 读完，手里已是**第二题** → 于是照着第二题点了第 1 个。

根子是：**这个动作是在第一题还在屏幕上时做的，却被执行到了第二题上。**

**规则覆盖的三种情况**：

- 连按两下 `1` → 第二下作废（屏幕已翻页），只点一次。
- 按错键马上按另一个改（屏幕**没**翻）→ 照常执行。这是用户早先明确要求保留的行为。
- 点了之后屏幕确实翻了页、用户又按了一个键 → 作废。因为它不可能是在回答
  他自己还没看到的新题。

**代价**：若用户在翻页那两秒多里**已经看到新题**并立刻按键，这一下会被丢掉，
需要再按一次。丢一下是「漏点」，代价低于「点错」—— 与本项目一贯原则一致。

## 3. 总体设计

### 3.1 架构选型（方案 A）

**界面占主线程，听语音挪到后台线程。**

Tkinter 要求它自己的事件循环跑在主线程，而现在「听语音 → 识别 → 点击」正占着主线程。
所以把这段抽成 `run_voice_loop()` 放到后台线程，主线程交给 Tkinter 的 `mainloop()`。

被否决的两个方案：

- **方案 B：界面自己开一个线程，主循环不动。** 改动最小，但 Tkinter 在非主线程运行
  不是官方支持的用法，退出时容易出问题。与「宁可慢不可错」的项目基调不符。
- **方案 C：界面独立进程，两边用 socket 通信。** 隔离最好，但要引入进程管理、
  通信协议、生命周期一大套机制，对这个规模的功能是过度设计。

### 3.2 数据流

```
   热键/小键盘线程 ──┐
                    ├──▶ 动作队列 ──▶ 动作工作线程
   GUI 按钮 ────────┘                （消费队列：按键、界面意图、退出）
                                          │  执行；结果推给 UiState
                                          │  需要时置位 wake_event
                                          ▼
                                     UiState（加锁的状态黑板）
                                          ▲
   监听线程 run_voice_loop ──────────────┘  听语音→识别→点击；结果也推这里
   （听/识别/点击）                        │
                                          │
   Tkinter 主线程 ── 每 150ms 轮询 ────────┘  渲染
```

**关键点：界面上每一个开关，调用的都是和热键完全相同的那几个函数**
（`voice_gate.toggle()` / `hotkeys.set_numpad()` / 切换 `ctx["mode"]` …），
不写第二套逻辑，因此不存在「界面显示开着、实际没开」这种分裂。

### 3.3 线程模型

| 线程 | 职责 |
|---|---|
| 主线程 | Tkinter `mainloop()`（`--gui` 时）；界面刷新、把按钮变成「意图」塞队列 |
| **动作工作线程** | 消费动作队列：小键盘按键、界面意图、退出。**沿用现有的 `numpad_worker`** 扩展而来，始终存在 |
| 监听线程 | `run_voice_loop()`：听语音 → 识别 → 点击。`--gui` 时跑在后台线程；不带 `--gui` 时仍跑在主线程（保持老行为） |
| 预读线程 | 现有的 `ScreenPrefetcher` 后台读屏 |
| keyboard 监听线程 | 现有的全局热键回调（只做置位/入队，快进快出） |

**动作处理和监听必须是两个线程。** 监听线程大部分时间阻塞在「等你说话」上，
如果让它同时消费按键队列，那按小键盘就没反应了 —— 现在的小键盘之所以能用，
正是因为它走独立线程。本期只把「消费动作队列」这一个职责扩展去兼管界面意图，
监听线程不碰队列。

**队列要统一。** 现在小键盘走 `numpad_queue`、界面按钮需要自己的通道，
两者都必须在「监听循环阻塞在等说话」时仍能被及时处理。
因此把两者合并成**一个动作队列**，由**动作工作线程**消费：

```python
("numpad", number, stamp)     # 小键盘 1~9
("next", stamp)               # 小键盘 0 / 语音「下一题」
("force_read", stamp)         # 小键盘 .
("intent", name)              # 界面按钮：toggle_voice / set_mode / ...
("quit", None)                # 退出
```

这样「界面点开关」的处理延迟上限就是动作工作线程的轮询间隔（0.2 秒以内），
不受监听循环阻塞的影响。

### 3.4 让开关「立刻生效」

监听线程大部分时间阻塞在 `listen_once()` 里（等用户开口）。
`listen_until_silence()` 已经在收音频的循环里**每 50 毫秒检查一次 `stop_event`**，
所以只要把 `stop_event` 传给它，就能随时把这次等待打断。

做法：给监听传一个「唤醒事件」（`wake_event`）。
界面点开关 / 切模式时，塞一条意图进队列；**动作工作线程**执行完这个意图后置位 `wake_event`，
让阻塞中的监听立刻返回 None，循环回到顶部重新判断（模式、语音开关都在这时重新读）。

同时把 `hotkeys.quit_requested` 也作为监听的中断条件 —— 于是**关窗口能立刻退出**，
顺带修掉现在「按 ESC 要等你说完这句才退」的老毛病。

细节：`wake_event` 在**每次进入监听之前清零**，否则会立刻再次中断，变成空转。

## 4. 模块设计

### 4.1 `ui_state.py`

**职责**：做界面和主逻辑之间唯一的共享状态。**全部逻辑放这里**，`gui.py` 只负责显示。
这样界面相关的正确性可以用普通单元测试保证，不必依赖真实显示器。

```python
@dataclass
class OptionView:
    index: int          # 从 1 开始
    text: str

@dataclass
class ScreenView:
    prompt: str = ""
    options: list[OptionView] = field(default_factory=list)
    source: str = ""            # "预读" / "当场读屏" / ""
    age_seconds: float | None = None
    page: str = ""              # quiz / detail / other
    ok: bool = False
    reason: str = ""

@dataclass
class InputEvent:
    kind: str           # speech / numpad / next / force_read
    label: str          # 识别出的文字 / "3" / "0" / "."
    detail: str = ""    # 置信度、耗时等
    outcome: str = ""   # "点了第 4 个" / "已忽略：界面已翻页" / "没匹配上"
    at: float = 0.0

class UiState:
    def set_screen(self, view: ScreenView) -> None
    def record_input(self, event: InputEvent) -> None
    def recent_inputs(self, limit: int = 5) -> list[InputEvent]
    def current_screen(self) -> ScreenView | None
    def post_intent(self, name: str) -> None
    def take_intents(self) -> list[str]
```

**实现要点**

- 一把 `threading.Lock` 保护全部字段。
- 输入事件用**固定长度的环形缓冲**（如 20 条）—— 界面只显示最近几条，不需要无限增长。
- 开关状态**不在这里存**。开关的真相源是那些活对象（`voice_gate.enabled`、
  `hotkeys.numpad_enabled`、`ctx["mode"]`、配置里的两个 bool）。
  界面每次刷新时通过 `collect_state()` 现读，避免「两份状态不一致」。

### 4.2 `gui.py`

**职责**：摆控件、连线、按时刷新。**不含业务逻辑。**

```python
class AppWindow:
    def __init__(self, root, collect_state, on_intent): ...
    def refresh(self): ...        # 由 root.after 每 150ms 调一次
```

- 刷新回调 `collect_state()` 由 `main.py` 提供，返回一个「显示用快照」
  （三块内容都是普通数据），界面只负责画。
- 按钮点击 → `on_intent(name)` → `main.handle_intent()`，由它塞进动作队列。
- 窗口：`root.attributes("-topmost", True)`；可拖动（Tk 默认行为）；
  几何位置从 `gui.window` 读，关闭时写回配置。
- 文字用等宽字体，避免数字跳动时布局抖动。

### 4.3 `main.py` 改动

- **抽出 `run_voice_loop(ctx, actions)`**：现在 `main()` 里那段 while 循环原样搬进去，
  改成从统一动作队列里取活干。`--gui` 时它跑在后台线程，否则仍跑在主线程（保持老行为）。
- **`collect_state(ctx) -> dict`**：读活对象 + `UiState`，拼出界面要显示的三块数据。纯读，可单测。
- **`handle_intent(name, ctx)`**：把界面意图翻译成实际动作（调 `voice_gate.toggle()` 等）。可单测。
- **`do_click()` 增加结果回报**：成功 / 被跳过 / 被时戳拦下，都写进 `UiState`，
  这样界面第三块能显示「最近一次点击的结果」。
- 退出路径统一：关窗口 / `ESC` / 队列里的 `quit`，都落到 `hotkeys.quit_requested`。

### 4.4 语音「下一题」

- `matcher.py` 新增控制语表与识别函数（纯函数，可单测）：

  ```python
  NEXT_PHRASES = ("下一题", "下一词", "下一个", "下一组", "继续", "next")
  def detect_control(text: str) -> str | None:   # 目前只会返回 "next" 或 None
  ```

- `handle_speech()` 里，**在选项匹配之前**先查控制语：
  命中且 `cfg.voice.next_command` 为真 → 调 `handle_next(ctx, source="语音")`。
- `handle_next()` 增加 `source` 参数，日志据此显示 `[语音]` 或 `[小键盘] 0`，
  避免语音触发却打成小键盘的日志。
- 缺少的配置项补上：`voice.next_command`（默认 **true**）、`gui:` 整段。

### 4.5 动作时戳

- `ScreenPrefetcher` 新增 `identity()`：返回**最近见过那一屏**的指纹
  （复用现有的 `signature()`：前台应用 + 题干 + 各选项文字），没有任何数据时返回 `None`。
- **入队时盖章**：热键回调把当前 `prefetcher.identity()` 一起写进队列项。
- **执行时核对**：`handle_numpad()` 取到要点的界面后，用 `signature(snap)` 和戳比对：
  - 两者都已知且**不同** → **作废**，不点击，日志与界面都写明「已忽略：界面在按键后翻页了」；
  - 相同、或戳为 `None`（无基准可比）→ 照常执行。
- 戳为 `None` 时不拦，是为了避免「刚启动、还没任何界面数据」时误伤第一次按键。

## 6. 容错与已知限制

| 情况 | 行为 |
|---|---|
| 没有装 Tkinter | 打印明确提示，**退回纯命令行模式**继续跑，不能因此起不来 |
| 界面窗口被关掉 | 视同退出请求，程序正常收尾 |
| 界面刷新时数据尚未就绪 | 该块显示「尚未读到」，不报错 |
| `identity()` 无基准（刚启动） | 不拦，正常执行 |

**已知残留风险（本期不修，记录在案）**：小键盘 `0`（以及语音「下一题」）
用的是**固定坐标、不读屏**，因此**连按两下 `0` 仍会点两次**，
第二下可能落在翻页后的新页面上。本期按用户要求保持「直给」，
若日后真的踩到，再给它加一道短时锁。

**另一处已有限制**：「按住说话」模式下，退出 / 切模式要等松开 F8 或录满上限
才生效（`record_while` 没有中断参数）。常驻监听模式不受影响 —— 那边靠 `stop_event`
可以随时打断。因为按住说话本来就是「按着不放」的短过程，影响很小，本期不动。

## 7. 测试策略

沿用现有两层验证（开发者侧单元测试 + 用户侧真机试跑），新增部分尽量落在可单测的一侧。

## 9. 已确认的设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 界面技术 | Tkinter | Python 自带、零依赖；用户 Python 3.14 很新，装 PySide6 有风险 |
| 窗口形态 | 置顶浮窗、手动拖动、记住位置 | 实现简单，不依赖别人的窗口位置 |
| 界面显示坐标 | **不显示** | 用户明确表示没意义；坐标仍进日志 |
| 语音「下一题」 | **直给**：说了就点，不读屏校验 | 用户选择：「答题页上点了就点了」 |
| 主线程归属 | 界面占主线程、听语音挪后台 | Tkinter 的硬性要求；比非主线程跑 Tk 稳 |
| 连按两下同一个键 | 加「动作时戳」，屏幕变了就作废 | 从根上区分「翻页了」与「没翻页」两种情况 |
| 开关真相源 | 活对象（不复制到 UiState） | 避免「界面显示开着、实际没开」的分裂 |
| 界面逻辑位置 | 全部放 `ui_state.py`，`gui.py` 只摆控件 | 让逻辑可单测，不依赖显示器 |
