## 【重要】任务 1 过程中抓到的真回归 —— 值得记住的教训

去掉时戳时把队列条目从三元组改成二元组，**漏了 `main()` 里界面按钮那条独立的内联 lambda**
→ 解包失败被 `except: return` **静默吞掉** → **界面上每个按钮都点了没反应**，
而 **300+ 条测试全绿**（没有任何测试走「界面按钮 → 入队 → 解包」这条路径）。

**结构性修法（已落地）**：把**所有**入队点收进 `make_action_putters()` 一个函数
（现在返回四个回调：on_option / on_next / on_force_read / on_intent），
这样格式由**一个可单测的地方**决定；并让「解包不了」出声（`say()` 警告），
只有「认不出来的 kind」才静默。

**教训**：入队格式与解包格式分散在两处时，改一处不会有任何测试报警。
**凡是「A 写、B 读」的二元契约，要么收进同一个函数，要么让不一致时大声失败。**

## 补充任务 6（用户点头后再推进一步）

**目标**：按键等在预读上时，**用第一次读到的结果就走**，不必陪它跑完「确认」那一次读。
把最长等待从约 5 秒压到约 2.4 秒（物理下限：读一次屏固定要这么久）。

**做法**：`trigger_after_click` 的「还是旧界面」分支改成「先存第一份 → 再读 → 再存」；
并加**代数护栏**（`_generation`）：`invalidate()` 换代，预读每次收结果前核对代数，
变了就作废 —— **否则那次还在跑的确认读会把点击前的旧屏写回缓存，下一次按键就拿过期坐标点了**。
代数核对与写入放在同一把锁里。

**结果**：332 → **334 全绿**，提交 `a14c26c`。

## 补充任务 7（用户第二次反馈：按键要「立刻执行」）

**问题**：用户快速连按两次时，**第二下的响应被拖到新题出现之后** —— 因为 `take_or_wait` 会睡等预读跑完。
用户要求在代码里复核，确认属实（`take_or_wait` 的 while 循环）。

**用户要的行为 + 理由**：不要吞、也不要排在读屏之后，**立刻执行**。
1. 误触时界面还没翻过去 → 点在已答过那题上，等于没反应；
2. 不是误触说明他已看到新屏 → 而**选项位置是稳的**（等距 188px；长题干整排挪 43px，行高 150、中心到行边 75px，不跨行）→ 同一相对位置还是那个选项。

**代价（已写进代码注释）**：要做到立刻，就必须用「**最近读到的那一屏**」的坐标 ——
这正是设计文档推翻过的「坐标复用」。区别在于这次用的是**最近一次真实读到的坐标**，
而不是「不读屏直接猜」。用户明确接受，并且明确**不要**时间保险。

**实现**：`grab_screen(allow_stale=)` 三档 —— 缓存有就用缓存；缓存空就用 `peek_with_age()`
立刻点（日志打出「那一屏是多少秒前读到的」）；一次都没读到过才当场读。
`handle_numpad` / `handle_next` 传 True，**语音路径一字未变**。

**结果**：334 → **341 全绿**，提交 `e3cd495`。

### 这个改动的风险（实现者推断，需上机留意）

最危险的一种：**手里那份是答题页、眼前实际是详情页**（答错后没按 0、又按了数字键）
→ 会静默点在详情页的随便哪个位置。反方向安全（详情页快照 `ok=False`，程序拒点）。
另外「选项换行占两行导致不等距」时行高不再是 150，旧坐标有机会落到相邻选项 ——
**这条是推算出来的，没在真机验证过**。

`handle_next` 另有一个洞：用旧屏时「下一题」按钮可能不在那份屏上（它只长在详情页），
那一按会什么都不点、只打提示。出厂配了 `fixed_next_position` 所以真机碰不到。

## 补充任务 8（用户第三次反馈：预读的内容根本不显示）

**问题**：界面和控制台只显示「点击前那一屏」，**永远慢一拍** —— 用户点完之后的几秒
（正是他要核对读屏对不对的时间）看到的还是上一题，等他按键才跳到当前题。

**根因**：喂界面的 `publish_screen()` 只在 `grab_screen()` 里调，也就是**只在准备点击的那一刻**；
预读在后台读完新题时只调 `note()` 存进缓存，**没播出去**。

**实现**：`ScreenPrefetcher` 加 `on_screen` 回调，`note()` 加 `source` 参数 ——
**每次存下一份新屏就播给界面和控制台**（内容没变则不播，免得刷屏）。
四处调用点各自标来源：预读 / 当场读屏 / 强制读屏 / 启动时读到。
`grab_screen` 里那处重复的 `publish_screen` 随之删掉。

**结果**：341 → **353 全绿**，提交 `f8d8e90`。

**顺手补的缝**：`ctx["ui"]` 原来建在预读器**之后**，于是启动那一屏播报时没地方放，
开窗后面板一片空白。把界面对象提到预读器之前建 —— 开窗即有内容。提交 `4dba75e`。

**遗留（实现者列出，未处理）**：
- `.` 强制读屏与「当场读屏」两条路，控制台会把同一屏**打两遍**（`note()` 播一次 +
  调用方原有的 `show_screen` 再打一次）。纯观感问题，没动。
- `trigger_on_speech()`（默认关）那处 `note()` 没传 `source`，所以不播。

## 补充任务 9（用户第四次反馈：连点丢预读 + 同一屏打两遍）

**问题一（严重）**：真机日志证明**连点两下之后一次预读都不剩** —— 缓存空、也没人在读。
根因是 `trigger_after_click()` 那句 `if self._busy: return`：第一下启动预读、
第二下换代后请求被**直接丢掉**、第一下读完又因换代作废。用户看到的就是
「读屏内容变成之前的了」。
用户要的行为：**每次点击都立刻中止上一次预读、并重新开始**。

**实现**：加 `_restart` 标记。忙的时候不丢请求、只置标记；正在跑的那轮一旦
发现自己作废，就在**同一个线程里**按当前代数与当前指纹重跑（把一轮抽成
`_prefetch_round`，`work` 改循环）。**不另起线程** —— 两个 dump 同时下命令会把
单次读屏从 2.4 秒拖到 8.5 秒（用户实测）。

**问题二**：预读读到新屏时播报了一次，用户按键时 `handle_numpad` / `handle_speech`
又把**同一屏**打一遍（用户原话：「之前展示了预读的，为什么我点击后又要展示一次」）。
**实现**：删掉那两句重复的 `show_screen`；「（界面来源：…）」那行和
`report_unusable_screen` 里那句保留。

**结果**：353 → **357 全绿**，提交 `1b542d2`。四条新用例都做过「改坏看红」。

**遗留（本次仍未处理，报告里已列）**：
- `handle_force_read`（`.` 强制读屏）那处 `show_screen` 简报没点名，**没删** ——
  它其实也是同一类重复（屏幕变了时控制台两遍）。要不要删请用户定。
- 「收尾那一瞬」与「读屏失败那一轮」两种窄缝里，请求仍可能被丢（按简报的
  「发现作废才重跑」实现所致）。要补可把判据从「这一轮返回作废」改成
  「代数真的换了」，一行的事。详见 `reports/r2-task-09.md` 的「疑虑 2」。
- `trigger_on_speech`（默认关）与 `trigger_after_click` 共用 `_busy`，语音预读
  在跑时会吞掉一次按键的预读请求（与改前一样，非本次回归）。
